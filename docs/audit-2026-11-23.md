## Детали

### B1 — fingerprint теряется в стриминговом ответе (High, bug)

**Evidence.** `probe.stream_request()` при `Content-Type: text/event-stream` вызывает
`_read_stream()` и собирает результат без `fp`:

```python
# rb_tui/probe.py:129-135
ttft, tts, total, tokens, chars, content = _read_stream(resp, start)
return _result("OK", ttft=ttft, tts=tts, total=total, tokens=tokens,
               chars=chars, content=content)
```

`_read_stream()` разбирает `usage`, но не читает `system_fingerprint` из событий.
`fp=` передаётся только в нестриминговой ветке (`:148`). Репродукция с SSE-событием,
содержащим `system_fingerprint`, даёт `r["fp"] == ''`.

**Impact.** `cli.run_probe_cycle()` передаёт пустой `fp` в `record_metric()`;
`metrics.add_metric()` добавляет `fp`/`fp_changed` только при непустом значении
(`metrics.py:41-49`). Следовательно `find_anomalies()` (`metrics.py:377-402`) и
`notify_anomalies()` (`alerts.py:205-210`) никогда не срабатывают в штатном режиме —
защита от подмены модели не работает. Тесты `test_metrics.py` проверяют только
логику `fp_changed` на готовых данных, а не сам извлечения.

**Fix (без новых функций).** В `_read_stream()` запоминать `event.get("system_fingerprint")`
и передавать его как `fp=` в `_result()` стриминговой ветки. Добавить регрессионный тест
на извлечение `fp` из SSE.

### B2 — неверный формат success rate в уведомлениях (Medium, bug)

**Evidence.** `find_anomalies()` кладёт доли 0..1:

```python
# rb_tui/metrics.py:367-375
"older_rate": round(older_rate, 2), "recent_rate": round(recent_rate, 2)
```

`render.py:372` умножает на 100 (правильно), а `alerts.py:201-203` и `:264` — нет.
Репродукция: `build_webhook_payload()` → `⚠ m: success 1.0 → 0.0`.

**Impact.** Алерты и Slack/Discord-сводки показывают «0.8%» вместо «80%».
**Fix.** Умножить на 100 в двух местах в `alerts.py` (или нормализовать формат в `find_anomalies` и поправить все три потребителя).

### B3 — HTML-экспорт не экранирует ID модели (Medium, security)

**Evidence.**

```python
# rb_tui/export.py:91,98
<td><code>{mid}</code></td>
<td title="first: {s["first_seen"]}, last: {s["last_seen"]}">...
```

`mid` приходит из удалённого каталога (`api.fetch_catalog()` → `save_catalog()` →
`load_metrics()`). Репродукция с ID `<img src=x onerror=alert(1)>` — сырой тег
попадает в HTML. В `dashboard.py` та же проблема уже решена через `esc()` и
`.replace("<", "\\u003c")`, то есть паттерн есть в репозитории.

**Impact.** Отравленный каталог → EXEC при открытии `--export-html` отчёта.
Смежно: `export.py:50-53` пишет CSV без `csv.writer`, поэтому запятые/кавычки/формулы
в ID ломают колонки и дают CSV-инъекцию в Excel.

**Fix.** `html.escape()` для `mid`, `status`, `first_seen/last_seen`, `last_error`;
`csv.writer` + `io.StringIO` для CSV. Тесты на экранирование.

### B4 — crash-отчёт утекает Slack-токен (Medium, security)

**Evidence.** Санитайзер требует буквальные слова `token|secret|webhook`:

```python
# rb_tui/crash.py:33-34
(re.compile(r"(?i)https?://[^\s\"'<>]*(?:token|secret|webhook)[^\s\"'<>]*"), ...)
```

Discord URL содержит `webhooks` и маскируется; Slack `https://hooks.slack.com/services/T.../B.../XXXX` — нет.
`diag_block()` (`crash.py:84`) кладёт весь `sys.argv` в отчёт, поэтому `--webhook <slack-url>`
сохраняется в `crash-*.log` и уходит в публичный GitHub Issue.
`test_crash.py:25-27` проверяет только Discord — слепое пятно.

**Fix.** Расшить шаблон на `hooks.slack.com` / `discord.com/api/webhooks` /
`api.telegram.org/bot` или явно маскировать значение `--webhook` в `sys.argv`.
Добавить тест на Slack-URL.

### B5 — `--prune-metrics` падает на битой записи (Medium, bug)

**Evidence.** `metrics.py:118-122` ловит только `ValueError`:

```python
ts = datetime.strptime(item.get("ts", ""), "%Y-%m-%d %H:%M")
except ValueError:
    removed += 1
```

Если `ts` равен `null` (поле есть, но None), `strptime` бросает `TypeError`.
Репродукция с строкой `{"model":"m","ts":null,...}` подтверждает падение.
Аналогичный цикл в «горячем хвосте» (`:139-143`) уже ловит `(ValueError, TypeError)` — непоследовательность.

**Fix.** `except (ValueError, TypeError)` в первом цикле. Тест на `ts: null`. Аналогичная
проверка в «горячем хвосте» (`:139-143`) уже корректна — привести оба цикла к одному виду.

### B6 — установщик пропускает проверку целостности (Medium, security)

**Evidence.**

```sh
# install.sh:76-88
if download "$tmp/$asset.sha256" ... ; then
    if check_sha256 ...; then ... else die "контрольная сумма не совпала"; fi
else
    say "==> контрольная сумма недоступна, пропускаю проверку"
fi
```

`update.py:142-145` при отсутствии `.sha256` наоборот отменяет обновление.
`install.ps1:40` тоже падает (у него `$ErrorActionPreference = "Stop"`).
Только POSIX-установщик ослабляет проверку — и это как раз тот путь, который
рекомендуется в README (`curl ... | sh`).

**Fix.** `die "нет файла контрольной суммы — установка отменена"`; при необходимости
явный opt-out через отдельную переменную окружения.

## Улучшения качества (без новых функций)

1. **Дублирование дефолтных промптов бенчмарка:** `probe.bench_model():257-261` и
   `cli._cmd_bench():698-702` — один и тот же список. Удалить копию в CLI, считать
   количество по `len(rows)`.
2. **Обход `sync.log_auto()`:** `cli.py:533-535` пишет в `auto-sync.log` напрямую,
   хотя есть `sync.log_auto()`. Использовать существующий helper.
3. **Falsy-провоки вместо `is not None`:** `render.py:206-209,229-233,465`, `cli.py:683`
   считают легитимное `0` («TTFT 0.000», «success 0%») как «нет данных». Заменить на
   `is not None`.
4. **Мёртвая логика в `crash.write_report()`:** `crash.py:156-159` инкрементирует
   `suffix`, но каждый раз заново генерирует timestamp — суффикс никогда не применяется
   к стабильному имени. Убрать или сделать детерминированным.
5. `metrics.prune_history()` — наивные `datetime` без时区; при смене TZ возможны
   пограничные ошибки. Низкий приоритет.
6. Тесты не покрывают B1–B5; добавить 5 точечных регрессионных тестов — это тоже
   улучшение без новых функций.
